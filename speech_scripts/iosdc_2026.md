## 章扉 1: 3Dモデルを用意して表示する

## Blenderでのモデリング

ディスクのモデルは、Blenderという無料の3DCGソフトでゼロからモデリングしました。これがそのモデリング画面です。

## 3Dモデルがアプリに表示されるまで

モデルがアプリに表示されるまでの流れはこうです。
Blenderでモデリングして、USDZという形式に書き出します。
それをReality Composer Pro——長いので、以下RCPと呼びます——のパッケージ形式、.rkassetsというフォルダに置きます。すると、Xcodeのビルド時に.realityという最適化された形式にコンパイルされます。
あとはRealityKitで読み込んで、タップ判定などの振る舞いをコードで付けていきます。

(原稿用のコード詳細: 読み込みは `Entity(named: "YugiohDuelDisk", in: bundle)` の1行。タップ判定は `generateCollisionShapes(recursive:)` + `InputTargetComponent` を付けるだけ)

## 正直に言うと…

プロポーザルには「BlenderやRCPを使って」と書いたんですが……正直に言うと、モデルづくりでRCPのアプリは一度も開いていません。

## BlenderとRCPの使い分け(実際はこうなった)

実際の使い分けはこうなりました。
形を作るのは全部Blender。RCPで使ったのは、さっきの.rkassetsというパッケージ形式だけです。
当初はRCPのGUIでコンポーネントを付けることも想定していたんですが、今回の実装は動的な要素ばかりで、結局ぜんぶコードで付けることになりました。
ただRCPのGUIが本領を発揮した場面もあって、それが召喚エフェクトです。これは3章でお話しします。

## 簡単なモデルならAIでも作れる(Blender MCP)

ここでひとつお伝えしたいのが、Blender MCPです。
MCPを使うと、ClaudeのようなAIがBlenderを直接操作してモデリングできます。「こういうモデルを作って」と頼むだけで、土台になる形は本当にできてしまいます。
細かい調整は人間が引き取る前提ですが、「3Dモデリングは経験がないから無理」と思っている方も、まずAIに任せてみると、意外なほど形になります。

## モデルに「ノード契約」を仕込む

モデルとコードの橋渡しで一番効いたのが、私が「ノード契約」と呼んでいる仕込みです。
Blenderには空オブジェクトという、形のない「目印のピン」を置く機能があります。
これをカードを置く5つのゾーン、デッキ、墓地、手首の固定点、ライフ表示の位置に、名前を付けて刺しておきます。
アプリ側は `findEntity(named:)` で名前で探すだけ。モデルの形を作り直しても、ピンさえ残っていればコードは無変更で動きます。

(原稿用のコード詳細: `disk.findEntity(named: "Zone_1_Field")` のように参照する。位置だけでなく姿勢も取れるので、カードの向きもピンに合わせられる)

## ノード契約の実物

実物はこんな感じです。左がBlender上のピンの配置、右がアプリでそれを参照している様子です。

## モンスターは1モデルで4バリエーション

たい焼きのモンスターは、カードによって中の具材が変わります。あんこ、クリーム、抹茶、チョコの4種類です。
これは4体分のモデルを作ったのではなくて、1つのモデルに具材4種を別パーツとして全部同梱して、実行時にカードに対応するパーツだけ表示しています。
使い分けの目安としては、形ごと変えたいならパーツ切り替え、絵だけ変えたいならテクスチャ差し替えです。

そして、これは実はいまこの場で動かせます。(右側のビューを操作)このように具材を切り替えると、モデルの中身だけが入れ替わります。ドラッグで回すこともできます。

(原稿用のコード詳細: 各具材パーツをEntityとして持ち、`root.findEntity(named: filling.rawValue)?.isEnabled = (candidate == filling)` で表示したい1つだけONにする)

## 章扉 2: Hand Gestureでカードを引く・持つ・置く

2章、Hand Gestureです。

## 土台は去年のHandGestureKitそのまま

ジェスチャー検知の土台は、去年のiOSDC2025の発表で作ったHandGestureKitをそのまま使っています。
去年は手話ジェスチャーの検知と翻訳というテーマで、ハンドトラッキングの可能性と限界を話しました。まだの方はぜひこちらもチェックしてください。

## ジェスチャーまわりの構成

ジェスチャー検知の基礎はHandGestureKitで、関節ごとのAnchorの追跡と、指先同士の距離の判定をしています。ここは去年と同じです。
今回のアプリに載せたジェスチャーは4つ。手首へのディスク装着、3本指の手札、ドロー、視線+タップでの配置です。
そして今回のアプリ側で新しく、指先だけでなく指の付け根——ナックルの位置にもアンカーを追加しました。これはHandGestureKitの機能ではなく、RealityKit標準の手の関節アンカーを直接張っています。なぜナックルが要るのか、理由は後ほど。

## 手首アンカーの子にすれば終わり……ではなかった

ディスクを手首に付けるだけなら、手首のアンカーの子にすれば終わり……と思っていたんですが、そうではありませんでした。

## ディスクを手首に「安定して」装着する

手首アンカーの子にすると、トラッキングが途切れた瞬間にディスクが消えたり暴れたりします。手首は視界の端に行きがちなので、ロストは頻繁に起きます。
そこで子にはせず、ワールド空間に置いたディスクが毎フレーム手首の姿勢を「追いかける」方式にしました。こうするとロスト中は最後の姿勢でその場に留まってくれます。
さらに、毎フレーム目標に35%だけ近づける、いわゆるローパスフィルタを挟んで、関節推定のブレを吸収しています。
実際に動いている様子は、冒頭のデモ1で腕にディスクが付いてきていたあの動きです。

(原稿用のコード詳細: 位置は `simd_mix(current, target, 0.35)`、回転は `simd_slerp(current, target, 0.35)`。35%は体感で調整した経験則で、Apple公式の推奨値ではない)

## 左手の3本指「つまみ」で手札を持つ

手札は、左手の親指・人差し指・中指の3本を合わせている間だけ、扇状に表示されます。
なぜ3本かというと、visionOS標準の2本指ピンチはタップ操作として予約されているので、混同しないためです。
そしてここがさっきのナックルの答えです。3本の指先を合わせると、指先は1点に集まってしまって、手の向きの情報が取れなくなります。なので扇の向きは、つまみ中も離れたまま並んでいる指の付け根——ナックルの列から計算しています。

(原稿用のコード詳細: 人差し指と小指のナックル位置から「指の並び方向」、指先とナックルの中点差から「指の伸びる方向」を作り、外積で手のひらの法線を出して手の姿勢を決めている)

## デッキからカードを引く(ドロー)

ドローは2段階のジェスチャーにしました。人差し指と中指でデッキに触れると「構え」、そのまま指を離すか引き抜くと「発火」でカードが1枚出ます。
束から1枚スライドさせて抜く、あの動作の再現です。
引いたカードは右手の指の間に追従します。

## カード配置: タップ先の判定

カードを盤面に置く操作は、visionOS標準の視線+タップです。
ポイントは、タップされたEntityが「5つのゾーンのどれなのか」の判定を、Entityの名前の文字列ではなく、自作Componentのタグで行っていることです。名前の文字列比較はモデルの構造変更に弱いので、ロード時に一度だけ名前で探してComponentを付け、以後はComponentだけを見ます。
さらに、いま持っているカードの種類に応じて、置けるスロットだけをハイライトしています。

(原稿用のコード詳細:

```swift
struct ZoneComponent: Component {
    let zoneIndex: Int
    let zoneType: ZoneType // monster / magic など
}

// ロード時に一度だけ名前で探してタグ付け
disk.findEntity(named: "Zone_1_Field")?
    .components.set(ZoneComponent(zoneIndex: 1, zoneType: .monster))

// タップ時はComponentを見るだけ
if let zone = tappedEntity.components[ZoneComponent.self] {
    place(card, at: zone.zoneIndex)
}
```

)

## 章扉 3: エフェクトとアニメーションでそれらしくする

3章、エフェクトとアニメーションです。

## 召喚シーケンスの全体像

召喚の演出は2つの場所で同時に起きます。
まずディスク上では、カードを置いたゾーンから盤面全体へ光のラインが走ります。
そしてフィールドでは、カードが出現して上昇し、足元で放射状の光のバーストが弾けます。
1秒後、光の中からモンスターがフェードインしながらせり上がってきます。
カードを置いた場所とモンスターが出る場所が離れているので、両方に演出を入れて視線を誘導するのが狙いです。

## 召喚バーストはRCPで作ったパーティクル

足元の光のバーストは、RCPのGUIで作ったパーティクルです。1章で「RCPのGUIが活きた場面」と言ったのがここです。
線・スパークル・光球の3つのエミッタを重ねていて、パラメータをスライダーでいじって即プレビューできるのはGUIならではでした。
visionOSにはブルームという「光があふれる」後処理がないので、加算ブレンドで白飛びさせて「白飛び=光」に見せています。
あとパーティクルが床を突き抜ける問題は、見えない壁——OcclusionMaterialの半球で下半分を隠して解決しました。

(原稿用のコード詳細: パーティクルは `ParticleEmitterComponent` として読み込まれ、`isEmitting` で開始/停止を制御。`restart()` は実行時にクラッシュする既知の落とし穴があるので使っていない)

## 竜の召喚エフェクトができるまで

この竜の召喚エフェクト、どう作ったかというと。
まず動きのシーケンスを、ぱらぱら漫画のような絵コンテとして作りました。何コマ目で光が出て、何コマ目で竜が現れて、という設計図です。
その絵コンテをベースに、さっき紹介したBlender MCP経由で、AIにモデルと動きを作ってもらいました。
ただ、細かい作り込みは自分の技術では手が届かず、正直このクオリティが今の限界です。それでも「絵コンテを描いてAIに投げれば、個人でもここまで出せる」というのは伝えたいところです。

## 同じ仕組みはiOS/iPadOSでも使える

3Dモデルの表示という意味で、2Dの写真より3Dモデルのほうが伝えられる情報は圧倒的に多いです。
実在するものなら、ARで実際の空間に投影して、実物大でより解像度高く確認することもできます。
そして1章の「ノード契約」と同じ仕込みで、見てほしいポイントにアンカーを置いておけば、タップでその部位にズームして詳細を見せる、という体験が作れます。

これも今ここで動かせます。(右側のビューを操作)モデルを回すと、手前を向いた部位にだけボタンが出て、タップするとその部位にズームして解説が出ます。

(口頭で軽く: ECの商品紹介や、教育コンテンツなんかに応用できると思っています)

## 再現してみてわかった制約

一方で、再現してみてわかった制約もあります。
まず腕とディスクのオクルージョン、つまり重なりの処理が不完全で、腕時計のように自然には隠れません。
手首のトラッキングは頻繁にロストしますし、速い動きには追従が遅れます。
あとはシミュレータではこの体験は確認できないこと、それから現実の部屋を光らせることはできないこと。このあたりは今のプラットフォームの限界です。

まとめです。

手首装着とジェスチャーは、ロスト・ブレ・つまみ中の縮退といった関節の特性込みで設計する必要があります。
制約は多いですが、「いつかやってみたかった」は、個人開発でも形にできます。
